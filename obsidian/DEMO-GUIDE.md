# CoreWise AI demonstration guide

CoreWise separates five evidence categories: USER_ENTERED hardware/configuration; ANALYTICAL estimates from the tested M2 equations; MEASURED explicit benchmark timings; PREDICTED trained-model outputs with their dataset provenance; and SYNTHETIC_DEMO illustrations/training data. SHAP_MODEL_ATTRIBUTION describes model behavior in ln(ms), not causal millisecond effects. Do not merge categories into a general hardware superiority claim.

## Preparation

Follow README setup, start PostgreSQL/app/private ML/worker, and keep runner execution separate. No live cloud deployment or external LLM connectivity is assumed. The Armoury Crate screenshot is absent; the interface is original CoreWise design based on written requirements, not a verified image reproduction. Prepare an account, known hardware specifications and documented capability assumptions. Demonstrate Obsidian/Frost/system themes and reduced-motion behavior. Never paste API keys into chat or reports.

## Presentation sequence

1. **Account and hardware:** Register/login, create a hardware profile and show USER_ENTERED labels. Explain unknown fields and that the browser cannot detect temperatures/utilization/fans. Set the default in Settings. Show session-protected personal routes and logout behavior.
2. **Workload:** Save a vector or matrix workload with explicit operation count, intensity, offloadable fraction, precision, footprint, transfer convention and repetitions. Label any illustrative assumptions. CPU GHz is not a FLOPS estimate.
3. **Analytical comparison:** Run M2 comparison, review component timings/model version, assumptions/sources/limitations and insufficient-data behavior. Explain transfer/launch costs for small work. This is a mathematical approximation, not a measurement.
4. **Local benchmark:** Open Benchmark Lab, explicitly pair the outbound-only runner, queue a bounded allowlisted job, then separately invoke `pnpm agent run --execute` on the authorized local device. Pairing/page load starts no work. Review raw samples, warmups, correctness, scope, environment and real CPU/GPU timings. If CUDA is absent, keep GPU null and demonstrate CPU-only raw CSV rather than inventing a paired target.
5. **Measured dataset:** For supervised paired training, collect at least 60 valid paired end-to-end samples across at least six distinct configurations/group identities. Supply externally sourced capability metadata and identify its actual source. Repeated samples from only one/two configurations cannot validate grouped generalization. Do not infer features from target timing. CPU-only samples remain raw records and cannot be relabeled as paired data.
6. **Models and prediction:** Import/save the measured dataset via the existing validator, train CPU/GPU models with group-aware splits, inspect actual validation/test errors and explicitly activate versions. Negative R² is possible. Generate a saved prediction from a matching workload/profile/precision/scope and review exact model/dataset references. A synthetic dataset can be used instead for an explicitly labeled engineering demonstration; do not call it measured accuracy.
7. **Explainability:** Request a saved prediction explanation, inspect separate device baselines, signed grouped contributions, log-space additivity and global held-out importance. State ln(ms), transformed-feature grouping and noncausality limitations. Missing artifacts/data do not produce invented SHAP values.
8. **Assistant:** With an explicitly configured tool-capable provider, ask about selected hardware, a saved prediction, benchmark scopes or its SHAP explanation. Show tool activity and actual source references. Without provider credentials, demonstrate the honest unavailable state. Automated mocked-provider tests verify protocol/integration, not external model quality or live connectivity.
9. **Reports:** Select owned hardware/workloads/comparisons/predictions/benchmarks/completed SHAP records, preview and generate an immutable report. Download PDF and CSV, inspect units/provenance/methodology/assumptions, and print the preview. Edit a source and reopen the saved report to show that historical evidence/export bytes remain stable. Delete a generated report with confirmation; source records survive.
10. **Overview and settings:** Return to the real owned dashboard state; show recent evidence/model readiness and report history. Settings provides themes/account/default hardware/model/runner/provider readiness and version. Paired-runner last-seen is not continuous online telemetry.

## Automated integration review

The M7 browser workflow can run independently with M7_FULL_LIVE_AUTH=1 to exercise actual registration → logout → login, followed by one owner's real six-configuration/60-sample CPU/GPU collection, measured ingestion, grouped fitting, prediction, SHAP, assistant protocol and report export. In the full suite, an exact test-owned database session fixture avoids exhausting the unchanged auth limit; preserved M1 tests still verify actual auth. The runner uses explicit --execute with small memory/size bounds. Capability fields in that integration are explicitly USER_ENTERED test assumptions, **not measured calibration**. The provider is an isolated test-only mock, **not a live external model**. Consequently a passing run proves plumbing/correctness/ownership, not calibrated predictive accuracy or the entire workflow live against an external LLM.

The ignored review PDF `corewise-evidence-review.pdf` and `m7-flow-evidence.json` under a unique `.artifacts/evidence/<report-id>/` directory are generated by the actual integration run when paired GPU support is available. They retain actual measurements and clear test-assumption labels; they are not seeded personal production records. Unsupported GPU environments skip that paired chain with a reason. Check STATUS for what actually executed on this machine.

## Honest limits to mention

No continuous monitoring, browser hardware sensors, hardware-attested CSV, automatic calibration, causal SHAP, autonomous benchmark/stress execution, or production deployment is claimed. Reports use an ASCII-safe PDF rendering for unsupported glyphs; full sanitized UTF-8 values are retained in CSV/snapshot. Chat text is buffered for credential filtering before chunks; tool activity streams during execution. Existing histories and report selections have documented bounds. Production TLS/proxy, external provider credentials and backup restore must be verified in their real environment.
